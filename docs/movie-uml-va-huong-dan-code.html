Luồng chạy qua các lớp

Create: POST /api/v1/admin/movies

  1. HTTP JSON được đọc thành CreateMovieRequest.
  2. MovieController đọc các thuộc tính và gọi MovieService.create(...).
  3. Service tạo Movie với UUID và timestamps, gọi MovieRepository.save(movie).
  4. Đối tượng thực thi là JpaMovieRepository; nó chuyển Movie sang MovieEntity.
  5. SpringDataMovieRepository lưu entity vào bảng movies.
  6. Adapter chuyển entity đã lưu thành Movie, trả về service rồi controller.
  7. Controller chuyển Movie sang MovieResponse và bọc SingleMovieResponse, trả HTTP 201.

Get: GET /api/v1/movies/{movieId}

  1. Controller nhận UUID và gọi service.getById.
  2. Service gọi repository.findUndeletedById.
  3. Adapter gọi Spring Data truy vấn id và deleted_at IS NULL.
  4. Có dữ liệu: Entity → Movie → MovieResponse → SingleMovieResponse → HTTP 200. Không có: Optional.empty(), ánh xạ 404 ở bước xử lý lỗi.

List: GET /api/v1/movies?page=1&pageSize=20

  1. Controller nhận page, pageSize và status (có thể null).
  2. Service gọi repository.findUndeleted.
  3. Adapter chuyển trang 1 thành trang 0, áp dụng sort, truy vấn Page<MovieEntity>.
  4. Adapter chuyển danh sách entity thành List<Movie>, lấy tổng số bản ghi và tạo MoviePage.
  5. Controller chuyển từng Movie thành MovieResponse, tạo PaginationMeta và MovieListResponse.
  6. Trả HTTP 200 với data là danh sách, meta là thông tin phân trang.

Mẫu movie-read.js: warm-up tách khỏi đo

Copy mẫu này vào file bạn tự tạo. Thay movieId bằng một phim tồn tại trong dataset. Script có warm-up 30 giây và pha đo 120 giây; cùng số VU. Mỗi iteration gửi một GET, quay vòng 3 loại request. Metric báo cáo chỉ lấy tag phase:measure.

import http from 'k6/http';
import { check, sleep } from 'k6';

const baseUrl = __ENV.BASE_URL || 'http://localhost:8080';
const movieId = __ENV.MOVIE_ID;
const vus = Number(__ENV.VUS || 25);
if (!movieId) throw new Error('Cần MOVIE_ID thuộc dataset test');

export const options = {
  summaryTrendStats: ['avg', 'med', 'p(95)', 'p(99)', 'max'],
  scenarios: {
    warmup: {
      executor: 'constant-vus', vus, duration: '30s',
      exec: 'readMovie', gracefulStop: '0s', tags: { phase: 'warmup' },
    },
    measure: {
      executor: 'constant-vus', vus, duration: '120s', startTime: '30s',
      exec: 'readMovie', gracefulStop: '10s', tags: { phase: 'measure' },
    },
  },
  thresholds: {
    'checks{phase:measure}': ['rate>0.99'],
    'http_req_failed{phase:measure}': ['rate<0.01'],
    'http_req_duration{phase:measure}': ['p(95)<500'],
  },
};

export function readMovie() {
  const n = __ITER % 3;
  const paths = [
    '/api/v1/movies?page=1&pageSize=20',
    '/api/v1/movies?page=1&pageSize=20&status=NOW_SHOWING',
    '/api/v1/movies/' + movieId,
  ];
  const res = http.get(baseUrl + paths[n], {
    tags: { name: n === 2 ? 'GET /movies/:id' : 'GET /movies' },
  });
  let body;
  try { body = res.json(); } catch (_) { body = null; }
  check(res, {
    'status 200': r => r.status === 200,
    'đúng envelope': () => body !== null && (
      n === 2 ? body.data && body.data.id === movieId
              : Array.isArray(body.data) && body.meta !== undefined),
  });
  sleep(0.1);
}

Threshold này là giả thuyết ban đầu trong SPEC, không phải kết quả đảm bảo. Với percentile/throughput tách theo route, giữ tags ổn định, không dùng UUID thành metric name. sleep(0.1) tạo think time; ghi giá trị này vì nó ảnh hưởng throughput.

Request chínhTỷ trọng theo SPEC

  1. Chuẩn bị ít nhất số tài khoản bằng số VU tối đa; lấy token đủ hạn trước pha đo. Login không được vô tình nằm trong mọi iteration trừ khi đang đo login.
  2. Mỗi VU có showtime/seat hoặc pool ghế độc lập. Dùng execution.vu.idInTest hoặc mapping fixture rõ ràng, không bốc ngẫu nhiên từ cùng một ghế.
  3. Chọn request chính theo tỷ trọng; mỗi iteration thực hiện một request chính. Với 35/25/25/10/5, có thể dùng vòng 20 lựa chọn: 7 Movie, 5 Showtime, 5 seats, 2 POST, 1 bookings/me; phân bố ngẫu nhiên hoặc luân phiên giữa VU và mô tả trong báo cáo.
  4. Sau POST 201, giữ bookingId và kiểm tra totalAmount/seat. Hủy đúng booking của VU để giải phóng fixture; đánh dấu request hủy phase:cleanup, không tính vào tỷ trọng/latency/throughput request chính.
  5. Cleanup vẫn dùng tài nguyên server; báo cáo phương pháp tái sử dụng ghế. Nếu giữ booking đến cuối, phải đủ pool ghế cho toàn bộ 2 phút và không cấp phát trùng.
  6. Đếm technical_error bằng custom Rate cho timeout/network/5xx/unexpected status; business_conflict bằng metric riêng cho 409. Không bỏ 409 rồi coi mọi request còn lại đều thành công.

Tag các request chính bằng phase warmup/measure; cleanup không dùng tag measure. Reset dataset cho mỗi lần lặp bằng công cụ seed chỉ dành cho test do nhóm thống nhất; không xóa data dùng chung.

Dùng http.expectedStatuses(201,409) cho request tranh chấp để metric failed mặc định không gộp 409 mong đợi với lỗi kỹ thuật. Đồng thời tự kiểm tra code SEAT_ALREADY_BOOKED; không coi mọi 409 là đúng. Script cần ngưỡng Counter sau chạy để fail nếu success khác 1, conflict khác N−1 hoặc unexpected khác 0.

Baseline trên Kaggle CPU và mẫu báo cáo

Chuẩn bị môi trường có thể tái lập

  1. Ghi Git commit/tag của bản đã ghép. Chạy clean verify trước; chỉ đo bản có test chức năng đạt.
  2. Trong notebook Kaggle CPU, kiểm tra internet, Java/PostgreSQL/k6 và cách chạy process. Không giả định Docker chạy được bên trong notebook. Nếu Docker khả dụng dùng Compose; nếu không, nhóm cần script khởi động PostgreSQL và jar như các process trong cùng môi trường.
  3. Ghi chính xác cách cài và version, CPU/RAM, giới hạn tài nguyên, JVM flags, Hikari connection pool, DB config, dataset/seed, số user/showtime/seat và timezone.
  4. Dùng loopback nếu client/API/DB cùng máy. Nếu khác máy, ghi topology và độ trễ mạng. Khi k6 cùng host với API, tải của k6 cũng dùng CPU/RAM; ghi riêng resource từng process.
  5. Khởi động API, chờ readiness UP, chạy smoke; seed fixtures ngoài pha đo.

Tài liệu này không xác nhận cấu hình Kaggle hiện tại hỗ trợ Docker. Kiểm tra trực tiếp trong session và ghi phương án thực tế; không dùng số đo local thay cho Kaggle mà giữ nguyên nhãn môi trường.

Quy trình đo mỗi lần

  1. Warm-up 30 giây, loại dữ liệu warm-up khỏi thống kê.
  2. Đo riêng 10, 25, 50 VU, ít nhất 120 giây mỗi mức. Lặp ít nhất 3 lần trên cùng cấu hình/dataset/phương pháp reset.
  3. Lưu raw metrics k6, log và resource samples có timestamp. Counter theo request và latency theo route/method; ghi grace period nếu có request kết thúc sau cửa sổ 120 giây.
  4. CPU/RAM: Docker thì thu docker stats theo chu kỳ; process trực tiếp thì dùng pidstat/psutil hoặc công cụ có sẵn. Ghi avg/peak CPU, RSS RAM của API và PostgreSQL, không lấy metric k6 làm CPU của server.
  5. Chạy contention riêng và lưu response counts cùng query DB chứng minh không double-booking.
  6. Chốt median của 3 lần cho từng chỉ số, kèm min/max hoặc độ dao động. Không trộn sample của các mức VU hoặc phần cứng khác nhau.

Throughput đo = số request chính trong pha measure / thời gian đo thực tế đã ghi; đơn vị req/s. Error rate kỹ thuật = lỗi kỹ thuật / số request chính; lỗi nghiệp vụ ghi riêng. Với contention, 409 đúng code là kết quả kỳ vọng. Không tính login/seed/cleanup/warmup vào cùng mẫu latency, nhưng phải mô tả tải phụ của chúng.
